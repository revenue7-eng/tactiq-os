# v2.1.0-rc14 errata

The v2.1.0-rc14 release assets covered by `SHA256SUMS` and their signatures
are unchanged. This document records two corrections made after publication.
Neither affects the published PCR reference values, the RIM, the evidence
archive `l3-evidence-rc14.tar.gz`, or any signature.

## 1. verify-l3-rc14.sh did not check that the archive holds only the listed files

`verify-l3-rc14.sh` verifies the archive's own `SHA256SUMS`, its signature,
and every file that list names. It did not check that the archive holds
nothing else. Two altered archives passed with exit 0:

- a file added to the archive that no list names;
- a genuine quote copied under a new number and left out of the list: the
  script found it, verified it and counted it.

Both need the archive repacked and its line in the release `SHA256SUMS`
rewritten, so the Sigstore check in `scripts/verify-release.sh` stops them,
and the script states that every line rests on that check. A replayed quote
states nothing false about the boot. But the number of quotes was then the
attacker's to choose, and the signed list did not bound what the archive
carries.

`verify-l3-rc14-v2.sh`, attached to the release on 14 October 2026, reads the
archive's table of contents before unpacking it. Every entry must be a
regular file directly under `l3-evidence-rc14/`, the archive's `SHA256SUMS`
must name each file once, and the archive must hold exactly the files it
names plus `SHA256SUMS` and `SHA256SUMS.p7s`. Otherwise the run fails. Found
by Capt Anil Sharma, who runs an independent implementation
(<https://ankr.in/tactiq-verification.html>).

The release `SHA256SUMS` lists `verify-l3-rc14.sh`, not the v2 script, so the
release signature does not cover it, and its self-check reports NOT
ESTABLISHED instead of PASS. Its SHA-256 is:

```
0222ca565b4542d135fe538dd3885ca0cfa97a692dddc4d99e1c274d4fe1b8ea  verify-l3-rc14-v2.sh
```

The same file is `scripts/verify-l3-rc14-v2.sh` in this repository.
`verify-l3-rc14.sh` and `VERIFY-L3-rc14.md` are left as published. This
errata is the correction.

## 2. verify-release.sh did not verify the log bundle

`scripts/verify-release.sh` checked the signature over `SHA256SUMS` with the
workflow certificate and signature, online, and never read
`SHA256SUMS.sigstore.json`, the bundle that carries the certificate, the
signature, the transparency log entry and its signed checkpoint. The bundle
is not in `SHA256SUMS`, since it signs it, so nothing else checked it. A
release with the bundle removed, the entry time moved or the checkpoint
altered passed. None of these changes a release file, but the bundle is the
only way to check a release without a network, and a damaged one went
unnoticed until it was needed.

From 14 October 2026 the script verifies the bundle the way
`release-sign.yml` does, against the same identity and issuer. A missing
bundle fails for rc12 and later, which carry one; rc11 has none. With
`--offline` the signature is checked through the bundle only, with no
network. Found with the altered sets of Capt Anil Sharma. On those sets the
script now accepts the genuine release and rejects all ten aimed at a
release checker.

This applies to rc12, rc13 and rc14 alike. The script is not a release
asset; it is used from this repository.
