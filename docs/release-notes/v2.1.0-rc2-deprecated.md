# TactiQ OS v2.1.0-rc2 — Deprecated

**Status:** Deprecated in favor of [`v2.1.0-rc3`](./v2.1.0-rc3.md).

`v2.1.0-rc2` is retained for historical reference. For any new
consumption, use `v2.1.0-rc3` — the binary payload is byte-identical to
rc2, and rc3 carries the canonical workflow-identity signature and the
full audit-readiness documentation set.

---

## Why deprecated

During rc2 release engineering, the `release-sign.yml` workflow was
triggered manually via `workflow_dispatch` from the default branch.
Sigstore's Fulcio issued a certificate whose Subject Alternative Name
encoded the triggering ref — `refs/heads/main`, not `refs/tags/v2.1.0-rc2`.
That certificate is cryptographically valid, but the SAN does not match
the tag, and Rekor recorded the signing event under a branch identity
that is not a valid trust root for a release.

The corresponding `.workflow.pem` and `.workflow.sig` assets were
deleted from the rc2 release page immediately. The **Rekor log entry is
append-only and cannot be removed**, however, which leaves a public
artifact whose identity is `refs/heads/main` associated with the rc2
`SHA256SUMS` hash. Rather than ship a release whose transparency-log
record is ambiguous, we re-signed the same binary payload on a fresh
tag (`v2.1.0-rc3`) using the correct tag-triggered workflow path, and
deprecated rc2.

## What is still valid on rc2

- **The binary artifacts.** `rootfs-rock5a.ext4`, kernel, DTB, SBOM
  bundle, aggregate SPDX, CVE reports, manifest, and buildinfo are
  unchanged. Their SHA-256 values in rc2's `SHA256SUMS` are the same
  as in rc3's.
- **The personal-identity signature** over `SHA256SUMS` —
  `SHA256SUMS.pem` and `SHA256SUMS.sig`, signed by
  `revenue7@gmail.com` via the GitHub OAuth OIDC issuer, Rekor index
  `1361157130`. Consumers who accept the personal identity can
  continue verifying rc2 with the procedure in
  [`VERIFY.md`](../../VERIFY.md) §4.2. The canonical path for new
  consumers is rc3 under the workflow identity.

## What is not valid

- Any Rekor entry for rc2's `SHA256SUMS` whose certificate identity
  resolves to
  `https://github.com/revenue7-eng/tactiq-os/.github/workflows/release-sign.yml@refs/heads/main`.
  Such entries exist in the public log and must be treated as
  **invalid for release trust**, even though the cosign verification
  of the hash itself would succeed if the broken `.pem`/`.sig` were
  still present. They are not.

## Migration

Switch to `v2.1.0-rc3`. Because the binary payload is identical, no
rebuild, reflash, or field update is required — only the expected
verification identity changes.

```sh
# Old (rc2, personal identity — still valid, but deprecated path):
--certificate-identity    revenue7@gmail.com
--certificate-oidc-issuer https://github.com/login/oauth

# New (rc3, workflow identity — canonical):
--certificate-identity    https://github.com/revenue7-eng/tactiq-os/.github/workflows/release-sign.yml@refs/tags/v2.1.0-rc3
--certificate-oidc-issuer https://token.actions.githubusercontent.com
```

See [`VERIFY.md`](../../VERIFY.md) for the full procedure.

## Lessons folded into rc3

The `workflow_dispatch` trigger was removed from `release-sign.yml` in
rc3. The workflow now runs only on tag push (`on: push: tags: ['v*']`),
which guarantees that the SAN of any signature it produces resolves to
`refs/tags/<TAG>`. Manual re-signing of an existing release is
intentionally no longer possible through this workflow — if a release
needs to be re-signed, it gets a fresh tag.
