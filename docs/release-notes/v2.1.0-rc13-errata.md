# v2.1.0-rc13 errata

The v2.1.0-rc13 release assets covered by `SHA256SUMS` and their signatures
are unchanged. This document records three corrections made after
publication. None affects the published PCR reference values, the evidence
archive `l3-evidence-rc13.tar.gz`, or any signature.

## 1. The warm-reboot disclosure is withdrawn

The RIM disclosures of rc12 and rc13 state that the TPM of the reference
platform is not reset by a warm reboot. `VERIFY-L3-rc13.md`, attached to the
release, repeats it after its list of results.

That statement is withdrawn. It contradicts the rc11 hardware record and the
measurement of 2 October 2026 with a development loader
(`measurements/tpm-quotes-dev-20261002.md`), in which a warm reboot reset the
TPM. The disclosure is corrected in the tree by #224. How the rc13 release
loader behaves on a warm reboot has not been observed. A TPM reset is in any
case not by itself evidence of a reboot: SPL drives the TPM reset line, and
the running system can drive the same GPIO.

The RIM is signed and is not edited. `VERIFY-L3-rc13.md` is left as published.
This errata is the correction.

Consequence for a reviewer: a pcrDigest that differs from the RIM shows that
the boot was not the reference boot. It must not be explained as a warm
reboot. `verify-l3-rc13-v2.sh` and later report it as a failure.

## 2. The VERIFY-L3 scripts could score a check that did not run

`verify-l3-rc13.sh` and `verify-l3-rc13-v2.sh` read the output of
`tpm2_checkquote` for the word ERROR instead of its exit status. With
tpm2-tools absent, or present and unable to load its libraries, both quotes
printed PASS. The overall result was still a failure, carried by other checks.

`verify-l3-rc13-v3.sh`, attached to the release on 2 October 2026, passes a
quote only when `tpm2_checkquote` exits 0, and reports a tool that is missing
or cannot run as a failure. Found by Capt Anil Sharma, who runs an independent
implementation (<https://ankr.in/tactiq-verification.html>).

The same defect sat in step 4 of v1 to v3: the two Infineon downloads ran
curl without `-f`, so an HTTP error page counted as a download and printed
PASS before the EK chain failed. `verify-l3-rc13-v4.sh`, attached the same
day, runs curl with `-f` and requires both files to parse as DER certificates;
otherwise it uses the copies in the archive and reports the independence of
the EK chain as not established, as it does when Infineon cannot be reached.
Also found by Capt Anil Sharma.

Step 8 of v1 to v4 has a related, narrower gap. It classifies each PCR in an
embedded Python fragment, and if that fragment raises, the step prints
nothing: the NOT ESTABLISHED lines for separator-only and unselected PCRs
disappear and the summary does not say so. It cannot add a PASS, and it does
not occur on the rc13 evidence, whose quotes and RIM pass every earlier step.
The script of the next release reports an empty step 8 as a failure.

## 3. A limit missing from the procedure

`VERIFY-L3-rc13.md` does not state that the release root is bound to the
signed set only inside this repository. Whoever controlled the repository
before the first release controls both the root and every manifest that names
it. The limit and the fingerprint of `release-root-r2.pem` are now stated in
`RELEASE_INTEGRITY.md`, section 7.3, together with the places outside the
repository where the fingerprint is printed.

## Remedy

The VERIFY-L3 procedure and its scripts were attached to rc13 outside
`SHA256SUMS`. The next release lists them in the signed `SHA256SUMS`, signs
the evidence archive's own sums under the release hierarchy, and carries the
corrected disclosure in its RIM.
