# TactiQ OS v2.1.0-rc3 — Release Notes

**Status:** Release candidate. Canonical successor to `v2.1.0-rc2`.
**Tag:** `v2.1.0-rc3` at commit `5adb346`.
**Machine targets shipped:** `tactiq-rock5a` (RK3588S).
**Yocto release:** `scarthgap`. Kernel: `linux-yocto` 6.6 LTS.

---

## What this release is

`v2.1.0-rc3` is the first TactiQ OS release whose artifacts are signed
under a **workflow identity** — the `release-sign.yml` GitHub Actions
workflow, triggered by the tag push, using Sigstore keyless signing.
Trust no longer terminates at a personal account; it terminates at a
branch-protected workflow on this public repository.

The binary payload itself is unchanged from `v2.1.0-rc2`: no Yocto
recipe, machine configuration, kernel fragment, or distro flag was
touched between the two tags. See
[`docs/reproducibility/v2.1.0-rc3.md`](../reproducibility/v2.1.0-rc3.md)
for the identity statement. `v2.1.0-rc3` is therefore a re-signing and
documentation release, and it supersedes `v2.1.0-rc2` for all
consumption going forward.

## Verification

The canonical verification procedure for this release is in
[`VERIFY.md`](../../VERIFY.md). The short form:

```sh
TAG=v2.1.0-rc3
ID="https://github.com/revenue7-eng/tactiq-os/.github/workflows/release-sign.yml@refs/tags/${TAG}"

sha256sum -c SHA256SUMS
cosign verify-blob \
    --certificate            SHA256SUMS.workflow.pem \
    --signature              SHA256SUMS.workflow.sig \
    --certificate-identity   "${ID}" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    SHA256SUMS
```

Rekor index for this release's cosign signature: **see below this
section after the release is signed** (the index is written into the
Rekor log at the moment of signing, and will be published as an edit
to these notes once the tag-triggered workflow run completes).

Rekor index: `1361817475`.

## Changes since v2.1.0-rc2

### Supply chain
- Release-signing workflow
  ([`.github/workflows/release-sign.yml`](../../.github/workflows/release-sign.yml))
  is now the canonical source of the `SHA256SUMS` signature. The
  workflow runs on tag push, signs with Sigstore keyless under
  workflow identity, verifies the signature against the expected SAN
  (`refs/tags/<TAG>`), and uploads the assets to the release.
- The `workflow_dispatch` trigger has been **removed** from
  `release-sign.yml`. Manual dispatch runs from the default branch
  and produces a certificate with a `refs/heads/main` SAN — a
  cryptographically valid signature that does not bind to the tag,
  and thus is not a valid release signature. This class of breakage
  occurred on `v2.1.0-rc2` and motivated the rc3 re-signing release
  (see the deprecation notice below).

### Documentation
- [`VERIFY.md`](../../VERIFY.md) — full verification procedure, two
  identity paths (personal for rc2 and earlier, workflow for rc3
  onward), expected SAN strings, failure examples, Rekor lookup.
- [`docs/reproducibility/v2.1.0-rc3.md`](../reproducibility/v2.1.0-rc3.md)
  — binary-identity statement pointing at the unchanged rc2 methodology
  and raw data.
- [`docs/release-notes/v2.1.0-rc3.md`](v2.1.0-rc3.md) — this file.
- [`docs/release-notes/v2.1.0-rc2-deprecated.md`](v2.1.0-rc2-deprecated.md)
  — rc2 deprecation rationale.
- `SECURITY.md` supported-versions table updated to reflect rc2
  deprecation and rc3 canonical status.

### Binary artifacts
- Root filesystem, kernel, device tree, manifest, buildinfo, SBOM
  bundle, aggregate SPDX, and CVE reports are **bit-for-bit identical**
  to the corresponding rc2 artifacts.
  `rootfs-rock5a.ext4` SHA-256:
  `55425ccc8b6d2a01ee9824fe96436ebb632b5a25ecc504d0ff4f7cca71b7e0e4`.

## Hardware support and performance reporting

Target platforms: Rock 5A (RK3588S), Rock 5B (RK3588), Rock 5T (RK3588),
generic ARM64 via Yocto machine configs. Additional RK3588-family
boards and a `qemu-x86_64` configuration are supported for build and
functional validation.

Performance metrics are published according to the TactiQ measurement
standard: multi-sample variance across board units, thermal envelopes
under sustained load, and runtime data from representative workloads.
Publication follows the full qualification cycle. Board-specific
qualification data, once released, will be linked from future release
notes.

## Deprecation of v2.1.0-rc2

`v2.1.0-rc2` is **deprecated in favor of `v2.1.0-rc3`**. The root cause
is a Rekor transparency-log entry created under the `refs/heads/main`
SAN by a manual `workflow_dispatch` run of the release-signing
workflow, which is not a valid release identity and cannot be removed
from the log. The affected workflow-identity signature assets were
deleted from the rc2 release, but the Rekor entry persists; the
cleanest remediation is to publish a tag-triggered canonical signature
on a new tag. Full rationale, including the rc2 personal-identity
signature that remains valid for anyone who prefers to continue using
rc2, is in
[`docs/release-notes/v2.1.0-rc2-deprecated.md`](v2.1.0-rc2-deprecated.md).

## Known limitations — roadmap to GA

This is a release candidate, not GA. The following items are
acknowledged gaps; each is tracked and has a named milestone rather
than a date. GA will be cut when every item below is either closed or
has an explicit, documented rationale for staying out of scope.

- **Full threat model document.** In progress. The individual
  components — SELinux policy, RAUC signing, IMA posture, attestation
  agent, release-signing pipeline — are each documented in place;
  a consolidated threat model tying them into a single adversary
  model is not yet published.
- **SLSA binary attestation.** Current attestation
  (`actions/attest-build-provenance@v2` in `attest.yml`) binds to the
  deterministic source archive only. Binary-level attestation — for
  `rootfs-rock5a.ext4` and friends — requires the full Yocto build to
  run inside GitHub Actions. Roadmap: stand up a minimal rootfs build
  (qemu-x86_64) in CI first, extend to Rock 5A afterwards. Tracked in
  [`SUPPLY_CHAIN.md`](../../SUPPLY_CHAIN.md#build-provenance).
- **Hermetic builder / SLSA L3 path.** The hosted runner used by
  `attest.yml` is sufficient for L2 but not L3. Reaching L3 requires
  a hermetic builder with controlled network and tooling, not the
  stock `ubuntu-24.04` runner. Not in scope for GA; explicitly
  roadmapped.
- **Dependency pinning audit.** GitHub Actions versions are pinned
  by Dependabot. The Yocto layer pins via `scarthgap` release and a
  specific kernel point-release. A full audit confirming that every
  transitive tool version used during the build is hash-pinned, with
  the same digests across independent builds, has not been published.
  Tracked.
- **Key rotation and revocation policy.** Sigstore keyless removes
  long-lived signing keys entirely, which eliminates most rotation
  surface. The remaining signing keys are the RAUC development
  keyring (in-tree, explicitly dev-only) and any future production
  keyring loaded from CI secrets. A written rotation and revocation
  policy for the production RAUC keyring is pending and will ship
  with the production-keyring work tracked in `SUPPLY_CHAIN.md`.
- **Hardware qualification matrix.** Per the TactiQ measurement
  standard (see README and the Hardware section above), qualification
  data is released as part of the qualification cycle, not ahead of
  it. The rc3 release ships functional artifacts; qualified
  performance figures are tracked separately.
- **Filesystem-image bit-identity.** 99.9433% byte-identity
  empirically measured in rc2 and unchanged in rc3. Remaining drift
  is localised to known non-deterministic ext4 metadata regions;
  driving this to 100% requires `mkfs.ext4 --uuid` pinning, inode
  timestamp normalisation, and deterministic `machine-id` /
  `random-seed` generation. Upstream Yocto work is in flight; we
  plan to adopt as it lands.
- **Two-person review gate on builder config.** Not wired today.
  Roadmap item tracked in `SUPPLY_CHAIN.md`.

Every item above is surfaced so consumers can make an informed trust
decision about this release candidate. Items are added to, not removed
from, the "Known limitations" section as they are identified; the
section only shrinks when a gap is actually closed.
