**Status:** Release candidate. Canonical successor to `v2.1.0-rc3`.
**Tag:** `v2.1.0-rc4` at commit `<TAG_COMMIT>`.
**Machine targets shipped:** `tactiq-rock5a` (RK3588S).

## What this release is

`v2.1.0-rc4` is a TactiQ OS release whose image has booted to a
verified login prompt on physical Rock 5A hardware. Boot was verified
on 4 May 2026 against an earlier rc3-base image (kernel
`6.6.123-yocto-standard`, SELinux enforcing, full LSM stack
`lockdown,capability,selinux,integrity`, IMA at PCR 10), and again on
6 May 2026 against the rc4 candidate image carrying the substance
changes described below — the migrated U-Boot path, the new extlinux
delivery class, and the WIC stale-bootloader fix.

The artifact set, signing regime, and verification procedure carry
forward unchanged from rc3: SHA-256 manifest, Sigstore keyless
workflow-identity signature on tag push via
[`.github/workflows/release-sign.yml`](../../.github/workflows/release-sign.yml),
SPDX SBOM, CVE reports.

## Changes since v2.1.0-rc3

### Boot path — U-Boot migration

The U-Boot recipe migrated from the denx.de mainline 2024.01 tree to
the Kwiboo fork at `2024.07-rc3` (commit `8cdf606e`), and `rkbin` moved
back to the versions Kwiboo qualifies against (`v1.47` for the
`rk3588_bl31_v1.47.elf` BL31 build, `v1.18` for the DDR init blob, in
place of `v1.51` / `v1.19`). BootROM offset values that were previously
inlined in `wks.in` were lifted into a new include file,
`meta-tactiq-bsp-rockchip/conf/machine/include/rk3588-bootrom.inc`, so
the contract between the bootloader recipe and the WIC image
description is captured in one place.

This migration is the path that produces a Rock 5A image that
reaches the BL31 hand-off and the U-Boot prompt. The denx.de mainline
path it replaces does not; the asymmetry is rooted in which BL31 / DDR
combination the upstream branch is tested against, and Kwiboo's branch
tracks the rkbin pair that the RK3588 family expects.

### Boot path — extlinux delivery

A new bbclass, `classes-recipe/tactiq-extlinux-deploy.bbclass`, wraps
the OE-core `uboot-extlinux-config` mechanism with explicit install and
deploy stages so that the generated `extlinux.conf` lands at
`/boot/extlinux/extlinux.conf` inside the rootfs and not only in the
deploy directory. The kernel bbappend inherits the new class. The
development image recipe (`recipes-core/images/tactiq-image-dev.bb`)
adds `kernel-devicetree` to `IMAGE_INSTALL`; without that package the
device tree blob does not enter the rootfs and the extlinux entry can
load `Image` but has nothing to point `FDT` at.

This is what makes the `LABEL TactiQ OS` extlinux entry produced by
the build path actually loadable by U-Boot at runtime.

### Boot path — WIC stale-bootloader fix

`conf/machine/include/tactiq-arm64-uboot-base.inc` now declares
`WKS_FILE_DEPENDS:append = " virtual/bootloader"`. Without this
dependency, the WIC image step silently consumes the bootloader
artifacts cached in the deploy directory from a prior build — a class
of bug where the produced image is internally consistent but contains
stale bootloader bytes that no longer match the current source tree.
Adding the explicit dependency makes the WIC step bind to a freshly
built bootloader from the same source state as the rest of the image.

### Core layer — vendor-agnostic posture

The header of `conf/layer.conf` now documents the scope of the
vendor-agnostic core layer explicitly, separating "what the core layer
defines" from "what each vendor BSP layer adds." This is editorial
rather than functional, but it captures the architectural distinction
that the Rockchip-specific machinery moved to
`meta-tactiq-bsp-rockchip` in earlier rc4 work and the core no longer
carries.

### CI — distribution sanity

`.github/workflows/ci.yml` no longer hardcodes `linux-rockchip` as the
required kernel preference target in the distro-sanity job. The check
now matches the current `PREFERRED_PROVIDER_virtual/kernel` for the
target machine, which is `linux-yocto` for the core targets carried in
this release.

## Hardware support and performance reporting

Target platforms: Rock 5A (RK3588S), Rock 5B (RK3588), Rock 5T (RK3588),
generic ARM64 via Yocto machine configs. The qualification platform
for this release is `tactiq-rock5a`; the other RK3588 board configs in
the tree are supported for build but have not been booted on hardware
in this release cycle.

Performance metrics are published according to the TactiQ measurement
standard: multi-sample variance across board units, thermal envelopes
under sustained load, and runtime data from representative workloads.
Publication follows the full qualification cycle. Board-specific
qualification data, once released, will be linked from future release
notes.

The following items remain open and are carried forward unchanged from
the rc3 release notes. Each is tracked and has a named milestone.

- **Full threat model document** — in progress; per-component docs in
  place, consolidated document not yet published.
- **SLSA binary attestation** — historical attestation binds to the
  source archive only; binary-level attestation requires the full
  Yocto build to run inside hosted CI. Tracked in `SUPPLY_CHAIN.md`.
- **Hermetic builder / SLSA L3 path** — explicit roadmap item; not in
  scope for GA.
- **Dependency pinning audit** — not yet published as an audited
  document.
- **SELinux policy supply chain** — `revenue7-eng/tactiq-os-selinux`
  has CI but does not yet carry tagged cosign-signed releases,
  `VERIFY.md`, or Rekor-anchored signature over compiled policy
  artifacts. Bringing the policy repo under the same regime is
  scheduled and is a precondition for the combined trust root claimed
  at GA.
- **Key rotation and revocation policy** — written policy pending,
  ships with the production-keyring work.
- **Hardware qualification matrix** — qualification data follows the
  qualification cycle; functional artifacts ship in this release.
- **Filesystem-image bit-identity** — 99.9433% byte-identity carried
  forward; remaining drift in known non-deterministic ext4 metadata.
- **Two-person review gate on builder config** — not wired today.

## Known limitations — new in rc4

- **U-Boot autoboot does not complete on the current Kwiboo path.**
  `bootflow scan` reports `Card did not respond to voltage select! :
  -110` on `mmc@fe2e0000` before the SD card is initialised. After a
  manual `mmc dev 1` from the U-Boot prompt the card initialises and
  the kernel and DTB load and `booti` succeeds. Tracked. Candidate
  resolutions: a custom `bootcmd` that issues `mmc dev 1` before the
  scan, a U-Boot patch in the SD-card init path, or a different SD
  card class. Not a blocker for this release: a successful boot to
  login is reproducible from the U-Boot prompt and is what the
  measured-boot chain is anchored against.

- **`data-tactiq-dirs.service` fails on first boot.** The service
  unit calls `install -d -m … -o … -g …` to create the
  `/data/tactiq/{keys,audit,certs,counter}` directory tree; the
  rootfs does not carry the `coreutils` `install` binary (BusyBox in
  the minimal hardened-edge profile provides `mkdir`, `chmod`, and
  `chown` but not `install`). Root cause is identified; the fix is to
  rewrite the service body in terms of the BusyBox-available
  utilities and ships in the next iteration. Tracked separately.

- **`systemd-networkd-wait-online.service` fails on the bring-up
  unit** because no network is wired to the development board.
  Environmental, not a release issue.

- **`tactiq-agent` on the Rock 5A produces an SELinux denial loop**
  in enforcing mode (`avc denied { map } shell_exec_t` for
  `/usr/bin/bash.bash`, followed by `SIGSEGV` and systemd respawn).
  This is the stub agent (`tactiq-agent-stub.sh` in
  `recipes-core/tactiq-agent/`) and the missing rule in the
  `tactiq_agent` SELinux policy module in
  `revenue7-eng/tactiq-os-selinux`. Does not affect boot or login.
  Tracked on a separate track tied to the agent v0.1 implementation
  described in [`ATTESTATION.md`](../../ATTESTATION.md).
