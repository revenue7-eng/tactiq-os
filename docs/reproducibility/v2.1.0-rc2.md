# Reproducibility measurement — v2.1.0-rc2

This document captures the raw data and methodology behind the
reproducibility figures cited in `SUPPLY_CHAIN.md` for the Rock 5A
rootfs image in `v2.1.0-rc2`. Raw `cmp(1)` output is retained alongside
this file so any third party can verify the numbers independently.

## TL;DR

Two independent `bitbake tactiq-image` invocations against the same
source tree produced `rootfs-rock5a.ext4` images with:

- **Identical file size** (369,253,376 bytes)
- **99.9433% byte-level identity** (209,509 differing bytes / 369,253,376 total)
- **Differences localize entirely to known non-deterministic ext4
  metadata structures** — primary + backup superblocks, inode tables,
  block group descriptor copies — with no content-file differences.

Per-file content reproducibility is further corroborated by the published
SPDX aggregate: all 7,178 files have identical SHA-256 hashes across
both builds.

Build A's hash is also present in the signed `SHA256SUMS` of the

## Method

```
cmp -l rootfs-A.ext4 rootfs-B.ext4 > cmp-raw.log 2>cmp-error.log
wc -l cmp-raw.log            # number of differing bytes
stat -c %s rootfs-A.ext4     # total size
```

Offset distribution, run-length statistics, cluster detection, and
ext4-structure mapping were computed from `cmp-raw.log` in Python. The
raw log (3.7 MB uncompressed, one line per differing byte) is retained
as `cmp-raw.log.gz` next to this document. The analysis script is
reproduced in full at the bottom of this file.

The low-density cluster at `0x49409` (3.90% density, 2.25 MiB span)
is the **primary inode table**: ~90,000 inode-table bytes touched
within a 2.25 MiB region, consistent with timestamp fields
(`i_atime`, `i_ctime`, `i_mtime`, plus their `_extra` nanosecond
halves) differing in each inode entry while the remaining 90%+ of
each inode stays identical.

The high-density clusters (78–80%) are 1 KiB spans corresponding
to individual backup superblock copies, each of which contains the
same set of timestamp + UUID fields differing.

## Interpretation

Observed differences correspond one-to-one to known non-deterministic
sources in the ext4 assembly pipeline. In rough order of contribution:

1. **Inode timestamp fields** (atime / ctime / mtime + nanosecond halves)
   written during `do_rootfs` / `do_image_ext4`, affecting every inode
   in the image.
2. **Block group descriptor timestamps** (primary + all backups).
3. **Primary and backup superblock fields** (`s_uuid`, `s_mtime`,
   `s_wtime`, error time fields).
4. **Small runtime-generated files** (`machine-id`, `random-seed`)
   on the rootfs — these show up as a handful of the medium-length
   runs but are already recorded with their hashes in the SPDX bundle
   (and are regenerated at first boot anyway).

Per-file content is reproducible; file **content** hashes recorded in
the SPDX aggregate (`sbom-image-rock5a-aggregate.spdx.json`) are
identical between the two builds for all 7,178 files.

## Known non-reproducible sources — closure plan

| Source                    | Mitigation                                       | Status          |
| ------------------------- | ------------------------------------------------ | --------------- |
| `s_uuid`                  | `mkfs.ext4 -U <fixed>` derived from `SOURCE_DATE_EPOCH` | roadmap  |
| Inode `atime`/`ctime`/`mtime` | `REPRODUCIBLE_TIMESTAMP_ROOTFS` + normalization pass post-`do_rootfs` | roadmap |
| `s_mkfs_time`, `s_wtime`  | `mkfs.ext4 -E mkfs_time=<epoch>`                 | roadmap         |
| `/etc/machine-id`         | Deterministic derivation or zero-at-image-time   | roadmap         |
| `/var/lib/random-seed`    | Remove from image; generate at first boot        | roadmap         |
| Backup SB copies          | Covered automatically once primary SB is pinned  | roadmap         |

See `SUPPLY_CHAIN.md` → *Short-term roadmap* item 3.

## Reproduce this analysis

The raw `cmp` log (`cmp-raw.log.gz`) and the two image hashes above
are sufficient for any third party to verify the figures. The
analysis script is:

```python
from collections import Counter

offsets = []
with open('cmp-raw.log') as f:
    for line in f:
        parts = line.split()
        if parts:
            try:
                offsets.append(int(parts[0]))
            except ValueError:
                pass

total_size = 369_253_376
diff_bytes = len(offsets)
print(f"Bit-identity: {100 * (total_size - diff_bytes) / total_size:.4f}%")

# Contiguous runs
offsets.sort()
runs = []
if offsets:
    start = offsets[0]
    length = 1
    for i in range(1, len(offsets)):
        if offsets[i] == offsets[i - 1] + 1:
            length += 1
        else:
            runs.append((start, length))
            start = offsets[i]
            length = 1
    runs.append((start, length))

print(f"Distinct runs: {len(runs)}")
print(f"Mean run length: {sum(l for _, l in runs) / len(runs):.2f}")
print(f"Max run: {max(l for _, l in runs)}")
```

Expected output given `cmp-raw.log.gz` and a file with
SHA-256 `55425ccc8b6d2a01ee9824fe96436ebb632b5a25ecc504d0ff4f7cca71b7e0e4`
compared against one with SHA-256
`61368e5b1916b8608341494d2e95e826307c61572e1777ec4c7a513ef0045934`:

