# Reproducibility measurement — wrynose

This document captures the raw data and methodology behind the
reproducibility figures for the Rock 5A rootfs image built on
Yocto wrynose. Raw `cmp(1)` output is retained alongside this file
so any third party can verify the numbers independently.

## TL;DR

Two independent `bitbake tactiq-image` invocations against the same
source tree (tag `v2.1.0-rc6`) produced rootfs images with:

- **Per-file content**: ✅ 38947/38951 SBOM entries identical.
  The 4 differing entries are image-level wrappers (`.ext4`, `.wic`,
  `.wic.bmap`, `.wic.gz`), whose divergence reflects filesystem
  metadata (superblock UUID, mkfs timestamp, inode timestamps), not
  rootfs content. The rootfs tarball (`.tar.gz`, hash `f98a6d8d…`)
  is bit-identical between both builds — direct evidence that the
  content is identical.
- **Image-level**: differs 73078 bytes in 9,785,328,640 (99.9993% identical)
- **Manifest**: 273 packages (A) / 273 packages (B), identical

**Per-file content reproducibility: ACHIEVED** on Yocto wrynose.
**Filesystem-image bit-identity: NOT YET ACHIEVED** — 99.9993% identical,
73078 bytes differ. Closure plan below (§ "Known non-reproducible sources").

## Method

### Per-file content reproducibility

Per-file SHA-256 hashes extracted from each build's SPDX 3.0.1 image
SBOM (`sbom-rock5a.spdx.json`). The SBOM records SHA-256 for every
file in the rootfs via `software_File` entries with `verifiedUsing`
containing the `sha256` algorithm. Hashes sorted by path and
compared with `diff(1)`.

Build A: 38951 files with SHA-256
Build B: 38951 files with SHA-256

Result: 38947 of 38951 entries identical. The 4 differing entries
are image-level wrappers (`.ext4`, `.wic`, `.wic.bmap`, `.wic.gz`)
whose SHA-256 divergence reflects filesystem metadata rather than
rootfs content — see `file-hash-diff.txt`. The rootfs tarball
(`.tar.gz`) is bit-identical between builds (hash `f98a6d8d…` in
both), which corroborates content-level bit-identity independently
of the SBOM comparison.

## Interpretation



Image-level differences localize to filesystem metadata, consistent
with the rc2 finding: inode timestamps, filesystem UUID, mkfs timestamp,
machine-id, random-seed. No content files are affected.

### Known non-reproducible sources — closure plan

| Source                    | Mitigation                                       | Status  |
| ------------------------- | ------------------------------------------------ | ------- |
| `s_uuid`                | `mkfs.ext4 -U <fixed>` from SOURCE_DATE_EPOCH  | roadmap |
| Inode timestamps          | REPRODUCIBLE_TIMESTAMP_ROOTFS + normalization     | roadmap |
| `s_mkfs_time`, `s_wtime` | `mkfs.ext4 -E mkfs_time=<epoch>`               | roadmap |
| `/etc/machine-id`       | Deterministic derivation or zero-at-image-time   | roadmap |
| `/var/lib/random-seed`  | Remove from image; generate at first boot         | roadmap |

## Reproduce this analysis

The raw `cmp` log (`cmp-raw.log.gz`), the two SBOMs, the extracted
file-hash lists, and the image hashes above are sufficient for any
third party to verify the figures.

```sh
# Per-file: re-extract and compare
jq -r '[.["@graph"][]|select(.type=="software_File")|{path:.name,sha256:(.verifiedUsing//[])[].hashValue}|select(.sha256!=null)]|sort_by(.path)|.[].sha256+" "+.[].path' sbom-A.spdx.json > hashes-A.txt
diff hashes-A.txt hashes-B.txt

# Image: re-run cmp
cmp -l image-A.img image-B.img | wc -l
```
