# Reproducibility measurement — v2.1.0-rc3

## Summary

The root filesystem image shipped with `v2.1.0-rc3` is **byte-identical
to the root filesystem of `v2.1.0-rc2`**. No Yocto recipe, machine
configuration, kernel config fragment, distro flag, or build tool
version changed between the two tags. The full reproducibility data,
methodology, raw `cmp(1)` output, and per-region analysis therefore
apply unchanged — see [`v2.1.0-rc2.md`](v2.1.0-rc2.md) and the raw log
at [`v2.1.0-rc2-cmp-raw.log.gz`](v2.1.0-rc2-cmp-raw.log.gz).

## Evidence

### Commits between tags

All commits landed on `main` between `v2.1.0-rc2` and `v2.1.0-rc3` are
documentation, CI wiring, or release-engineering — none touch the
build graph for the rootfs.

```
git log v2.1.0-rc2..v2.1.0-rc3 --oneline -- \
    conf/ recipes-core/ recipes-kernel/ scripts/ wic/
```

Expected output: empty.

### What changed in `v2.1.0-rc3`

- Release artifacts signed under the **workflow identity** produced by
  [`.github/workflows/release-sign.yml`](../../.github/workflows/release-sign.yml)
  on the `refs/tags/v2.1.0-rc3` tag push, instead of the personal
  identity used for rc2.
- Documentation additions:
  [`VERIFY.md`](../../VERIFY.md),
  [`docs/release-notes/v2.1.0-rc3.md`](../release-notes/v2.1.0-rc3.md),
  this file.

No binary regenerated between the two tags. `v2.1.0-rc3` is a
pure re-signing and documentation release; it is canonical going
forward, and `v2.1.0-rc2` is deprecated — see the deprecation notice
on the GitHub release page for rc2 and
[`docs/release-notes/v2.1.0-rc2-deprecated.md`](../release-notes/v2.1.0-rc2-deprecated.md).

## Status of filesystem-image bit-identity

Unchanged from rc2: **99.9433%** byte-identity across two independent
builds from the same source, with differences localised entirely to
known non-deterministic ext4 metadata fields (primary and backup
superblocks, inode timestamps, block-group descriptor copies). Per-file
content bit-identity is verified via the SPDX aggregate (7,178 files
with identical SHA-256 hashes across both builds).

The remaining filesystem-image drift and the path to full bit-identity
are tracked in [`SUPPLY_CHAIN.md`](../../SUPPLY_CHAIN.md#reproducible-builds)
and in the rc3 release notes under "Known limitations".
