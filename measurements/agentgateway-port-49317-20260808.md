# agentgateway listener port in base policy -- 2026-08-08

The `agentgateway` SELinux module declared `agentgateway_port_t` and stated
in a comment that the number was bound to the type by `portcon` in the same
file. It was not, and could not be. This record establishes what the parser
actually accepts, why the number itself was wrong, and what the corrected
policy produces in a real build.

Corresponding change: `tactiq-os-selinux` commit `3873e72`,
branch `feat/agentgateway-selinux`.

## Summary

Two independent defects, both in the shipped-but-unbuilt module.

`portcon` is rejected in a loadable module. Operators that bind a context to
a number are accepted only in the base policy. The `allow` rule naming
`agentgateway_port_t` therefore compiled against a type that no port carried,
and a bind would have been checked against whatever type the number already
had.

The number was 49190, which falls inside the `virt_migration` range
(49152-49216) already declared in `corenetwork.te.in`. Even with a working
binding mechanism, that number was unavailable.

Both are fixed by declaring the type and the number with `network_port()` in
the base policy, via a patch to `corenetwork.te.in`, on TCP 49317. The module
consumes the generated `corenet_tcp_bind_agentgateway_port()` and no longer
declares the type itself.

## What was executed

### 1. Does `portcon` compile in a loadable module

A synthetic module in the bare policy language, no refpolicy macros and no
refpolicy headers, so the answer isolates the operator and nothing else:

    module porttest 1.0;
    require { type unconfined_t; class tcp_socket name_bind; role object_r; }
    type porttest_port_t;
    allow unconfined_t porttest_port_t:tcp_socket name_bind;
    portcon tcp 49190 gen_context(system_u:object_r:porttest_port_t,s0)

    $ checkmodule -M -m porttest.te -o porttest.mod
    porttest.te:13:ERROR 'syntax error' at token 'portcon' on line 13
    checkmodule: error(s) encountered while parsing configuration
    EXIT=1

The error is on `portcon` itself. The parser never reached `gen_context`, so
this is not a macro-expansion failure -- the operator is not accepted here.

### 2. Is 49190 available

    $ grep -n -E "49[0-9]{3}" corenetwork.te.in
    190:network_port(matahari, tcp,49000,s0, udp,49000,s0)
    296:network_port(virt_migration, tcp,49152-49216,s0)

49152 <= 49190 <= 49216. The number is inside the `virt_migration` range.

### 3. Is 49317 available

    $ grep -n "49317" corenetwork.te.in
    (no match)

Nearest declared neighbours are 49216 below and 50000 above. In the IANA
dynamic range (49152-65535).

### 4. Build with the corrected policy

    $ bitbake refpolicy-targeted
    NOTE: Tasks Summary: Attempted 1932 tasks of which 1911 didn't need to be
    rerun and all succeeded.

`do_patch`, `do_configure`, `do_compile`, `do_install` all succeeded.
`do_compile` is where `checkmodule` and `checkpolicy` run, so a rejected
operator or a colliding `portcon` would have failed there.

### 5. Did the rule reach the policy

Patched source:

    $ grep -n "49317" sources/refpolicy/policy/modules/kernel/corenetwork.te.in
    95:network_port(agentgateway, tcp,49317,s0)

Generated by the refpolicy port generator, in the file that compiles into the
base policy:

    $ grep -n "49317" sources/refpolicy/policy/modules/kernel/corenetwork.te
    145:portcon tcp 49317 gen_context(system_u:object_r:agentgateway_port_t,s0)

## Limits on the above

The binary policy was not read directly. `seinfo` from the installed
`setools` refuses policy version 35 ("A binary policy must be specified"),
so the chain is established from the patched source, the generated
`corenetwork.te`, and a successful `do_compile` -- not from `policy.35`
itself.

No hardware. The board was not booted with this policy, no listener was
started, and no bind was attempted. That a bind on 49317 succeeds under
enforcing is not established here.

The recipe still carries 49190. `agentgateway_1.1.0.bb`, its
`agentgateway.service`, and `config.yaml` live in the `tactiq-os` tree on
`feat/bsp-kernel-fragment` and were not changed. Until they move to 49317
the policy and the daemon disagree.

The log rules in the module assume `/var/log/agentgateway` exists. Under
`ProtectSystem=strict` the unit cannot create it; `agentgateway.service`
needs `LogsDirectory=agentgateway` and does not carry it. Not exercised
here either way.

No firewall rule for 49317 exists. The `config.yaml` comment describes
three containment layers (systemd, iptables, SELinux); this record covers
the third only.
